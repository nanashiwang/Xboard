# Agent Note: 主域故障时的客户端恢复与多入口规划

Status: proposed

## Problem

用户报告 taige.us 无法访问，随后指出客户端也无法连接，希望规划尽量不影响客户体验的恢复方案。2026-11-02 同局域网无代理 Windows 已证实错误 DNS 解析，固定权威 IP 后带主域 SNI 的 TLS 仍重置；board.taige.us 有成功样本但一个 IPv6 地址超时。详细证据见[诊断进展](../../../../progress-log.md#2026-11-02taigeus-国内无代理访问诊断)。

目标是已连接用户尽量继续使用，断开及重启用户能恢复，新用户能登录，后续入口失效无需客户修改 DNS 或重装。旧版固化的账号与更新入口均受阻时，服务端不能直接修改已安装二进制；本次需要为部分客户提供一次覆盖升级，不能承诺所有旧版完全无感。用户此次具体客户端版本、错误及实际节点流量尚未现场验收，控制服务故障能解释现象，但不证明所有节点健康。

## Proposal

### P0：先确认恢复路径，保护仍在使用的客户

- 使用自有测试身份逐层验收控制 API、实际本人配置、节点 TLS/代理请求和出口；不能以网站 200 或节点延迟替代转发成功。优先区分已连接、断开待重连、重启、未登录及第三方订阅客户端五类用户。
- 复用 board 作为临时网页与修复包入口，核验完整登录授权、实际下载链接、索引及安装包均不会指回不可达主域；其同主域和 IPv6 波动使它不适合作为唯一长期备用。先验证再提供客户恢复指引。
- 已连接客户不因官网故障被要求退出、卸载或刷新全部节点；服务入口修复不重启健康内核、不改变套餐、节点身份或独享固定出口。真实节点失败另行处理。
- 旧主域及证书保持兼容，停用受影响入口的推广而不直接删除记录；此时 DNS 改 IP、开启 CDN 或 HTTP 301 均不能保证让已被域名拦截的旧客户端恢复。

### P1：发布一次可覆盖升级的恢复版本

以恢复现有用户为首个交付单元，不等待 P2/P3 全部完成。至少接入一个经业务验收的可达入口，并内置两个不同注册主域的可信控制入口；board 可作短期补充，不能占据两个独立主域的名额。新增域名的具体名称、所有权与证书需实施前确定，本提案不购买或切换域名。

统一入口选择用于 API、浏览器授权、订阅下载、套餐/客服/注册链接及邀请链接。优先上次成功入口；只对无副作用健康探针做有界竞速，验证 TLS、预期服务标识和响应结构后再发送认证请求；网络变化后重新探测，连续失败退避，恢复需稳定观察，避免来回切换。候选应具有线路差异，最终避免两个入口同时依赖同一个故障跳板；先复用现有后端与账号数据库，不在应急期做多主数据库。

IPv4/IPv6 采用有界交错尝试，不能等坏 IPv6 长超时后才走 IPv4，也不要求客户关闭全机 IPv6。备用健康时，将控制入口发现/切换的 P95 不超过 5 秒作为待验目标，不作为全网保证；首轮候选并发不超过两个，并设总预算，不串行叠加各 20 秒超时。[RFC 8305](https://www.rfc-editor.org/rfc/rfc8305.html)可作为双栈策略依据。

登录和续期保持串行。一次浏览器授权固定已选入口；途中失败不能把网页秘密或桌面令牌搬到任意域名。GET 和公开探针可以在可信入口间有限重试；刷新令牌、授权兑换、订单和支付等有状态请求不能盲目重放，尤其不能并发刷新同一凭据。需要无感恢复丢失响应时，再设计设备绑定、请求键、短期受保护结果保存和过期销毁的服务端幂等契约；完成前保持明确失败和受控重试。依据 [RFC 9110 重试语义](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)。

同时修正状态分类：目前 Account.renew 会仅凭 401/403 清理会话，应区分经过验证的账号撤权响应与 CDN/WAF 页面、非预期响应、DNS/TLS/超时。网络故障显示“服务连接暂时异常，正在尝试备用线路”，不误报套餐过期或直接清登录；明确过期、封禁、设备撤销与流量耗尽仍执行原限制。

更新入口与账号服务分开安排故障路径。索引和安装包均具备经验证的备用来源，扩展白名单但保持 HTTPS、预期路径、版本、摘要和更新签名检查；不能只复制索引、让其中安装包 URL 仍指回主域。保持应用 ID、数据目录、凭据库键名、设备 ID、更新公钥和安装格式，支持覆盖升级；令牌尚有效时复用登录，已失效者最多重新授权一次。现有 Tauri 更新签名不等于平台发行者签名或公证，交付须分别报告。

[Tauri 更新文档](https://v2.tauri.app/plugin/updater/)要求签名验证并支持多个索引端点；仍必须针对当前锁定的 updater 2.14.0 实测 DNS、TLS、连接超时、异常 200 和安装包下载失败，不能凭多 URL 配置宣称整条链路自动恢复。彻底失联的旧版无法通过同一受阻更新地址获救，需要从可达下载页覆盖安装修复版；不能依赖“另开系统代理”绕过当前 no_proxy。

### P2：控制服务离线时，允许已有用户继续或恢复连接

新增最近有效配置缓存，按账号/设备隔离、使用系统安全存储保护的密钥加密、私有权限和原子替换；仅在完整校验及内核应用成功后推进有效版本。缓存记录配置摘要、原账号/设备、签发时间、有效期、套餐边界和上次成功入口；明确退出/换号/撤权删除对应缓存，不能读取其他账号的旧文件。

服务端签发绑定配置摘要和设备的短期离线许可。建议初始宽限上限 24 小时且不超过套餐到期时间，作为待压测和业务核验的默认值；不是无限续用，也不按每次启动重新计时。发现时钟回拨或许可/缓存异常时要求在线验证；已收到封禁、到期、耗尽或撤销结果不得以缓存覆盖。首次安装、无有效缓存或许可过期者继续通过可达入口在线验证。

允许已登录、有有效缓存及许可的用户在账号服务暂时不可达时主动连接，后台低频恢复同步；应用重启也能准备缓存内核，不自动接管系统代理。账户信息标注最后同步时间，不把旧余额当实时值。节点侧仍强制执行用户鉴权、流量和停用规则；确认服务端实际撤权与计量约束有效后才启用离线宽限，不通过放开后端权限换取连通。

若用户已有健康连接，可后续增加“控制请求经本应用受控回环通道”的有界备用路径，避免依赖任意系统代理；须检查当前核心所有权、防止递归 DIRECT 规则和控制/业务请求混淆。未连接用户仍必须能依赖直连独立入口启动，不能以先连节点才能登录形成循环依赖。

### P3：入口可更新、可监测，客户不再手工换网址

在两个独立可达位置分发签名入口清单，客户端内置发现地址及独立验证公钥；记录版本、有效期、服务标识、允许来源、能力与撤销信息，防回滚，保留上次验证成功清单。主入口失效时仍能发现新入口。未知来源、重定向或错误签名不接收用户凭据；有效期届满的远程清单不能无限延期，按明确的内置入口与人工恢复路径退化。

控制 API、安装包分发、客户状态页和节点入口分担故障范围，避免全部放在同一个注册域、跳板或不可替代的解析链。签名清单也不是无限可达保证；所有内置地址同时不可达时仍需要已知的独立恢复渠道。后端容灾与数据恢复另立任务，不能把多域名接同一数据库称作完整高可用。

至少两个真实国内无代理观测网络与一个境外对照检查 DNS、TCP、TLS、公开 API、更新索引/包头及受控节点转发；当前证据只有一个国内局域网，不能冒充多运营商覆盖。告警按持续失败及对照结果收敛，不因一个探针瞬时失败全局切流；恢复后观察再回切。监控日志只保存分类和聚合耗时，不含订阅 URL、令牌或客户身份。

### 发布与用户体验

| 用户状态 | 希望达到的行为 | 边界 |
| --- | --- | --- |
| 正在连接 | 控制服务换入口不重启内核，业务继续 | 节点/出口本身故障不能保证旧会话不断 |
| 已登录但未连接 | P1 自动找到可达服务；P2 可在许可内用缓存连接 | 当前旧版尚无离线启动能力 |
| 应用重启 | 原账号、模式、规则与节点选择保留；有效缓存可恢复 | 不静默开启用户未启用的系统代理 |
| 新装或退出登录 | 可达入口完成一次登录授权 | 浏览器换主域可能需要登录一次，不能跨域复制 Cookie |
| 旧版完全失联 | 从备用入口一次覆盖升级 | 不承诺不可达旧版能原地自动更新 |
| 固定住宅出口客户 | 控制入口变化不改变专属出口 IP | 节点故障不擅自换国家或固定出口 |

先以专用测试账号和 Windows/Mac 无代理环境验收，再小范围安装，观察登录成功、连接成功、丢会话和更新失败后逐步扩大。第三方客户端另行提供同一账号的备用订阅地址，先验地址生成和导入，不轮换客户 token，不批量让用户删除旧配置。对已有可用连接不强制立即更新；提供空闲时升级及手动安装入口。公告先备好草稿，用户授权发送后再触达客户；不能只把公告放在已打不开的主域。

### 故障期间的客户触达

现有[管理员群发](../../../../app/Http/Controllers/V2/Admin/UserController.php)支持指定/筛选用户，使用 [SendEmailJob](../../../../app/Jobs/SendEmailJob.php) 的 send_email_mass 队列及既有 SMTP；[Horizon 配置](../../../../config/horizon.php)包含队列。生产投递仍须单独验证，接口入队成功不等于收件箱送达，更不等于客户已阅读。当前[桌面公告](../../../../desktop/capybara/src-tauri/src/notices.rs)仍读取 account::ORIGIN，没有独立推送，不能依靠在主域发新公告覆盖失联用户。

建议优先向有效套餐及近期使用客户的已登记邮箱发送服务故障说明，说明已知影响、现阶段可做的操作及经过验证的备用说明入口；修复版完成安装与业务验收后再发送一次恢复通知，含明确版本、可达下载链接和覆盖安装步骤。发送前先用获授权的自有邮箱验投递与链接，正文和模板按钮都不能重新指向失效主域；复用已有客服群/联系方式补充，站内公告覆盖仍在线用户。未授权不发送，未就绪不写“修复版已发布”。没有有效邮箱或已有客服联系方式者，本次不能保证主动联系到。

恢复版还应内置本地网络异常提示：连续服务连接失败时显示“服务连接异常”以及预置的独立恢复/支持入口，不靠从服务器获取文案；不能自动把所有网络故障断言为被墙。此能力须随新版本交付，无法反向补进当前失联旧版。

## Alternatives considered

- **只换 DNS、IP 或开 CDN**：服务端操作少且可保留旧地址，对普通解析/路由故障有效；本次指定正确 IP 后仍 TLS 重置，不能作为完整恢复方案。
- **客户端仅改为 board**：最快利用已存在入口，适合应急版本；同一注册主域仍有共同风险，单入口模式会复发，必须同时铺设独立入口和后续发现能力。
- **要求客户开别的代理或改 hosts**：可对个别环境临时排障，但增加使用门槛，当前原生 HTTP no_proxy 且 hosts 无法消除 SNI 干扰，不作为产品恢复流程。
- **马上建设多云多主数据库**：可降低源站故障影响，但本次主要是用户到入口受阻，多主会引入订单、额度及一次性令牌一致性成本；先复用单一账号权威，后端灾备单独规划。
- **只增加长期本地缓存**：能减轻控制网络依赖，但单凭旧套餐状态无法及时识别撤权和到期；采用签名、有界许可并保留节点端强制约束，不无限信任旧状态。

## Acceptance criteria

1. 分别注入 DNS 错误、正确 IP 下 SNI/TLS 重置、单 IPv6 黑洞、HTML 403/异常 200、超时、索引正常但包地址坏；可信备用可达时自动恢复，错误响应不清会话、不破坏有效配置。P95 切换目标以真实统计验收。
2. 同一有效账号在旧版覆盖升级、冷启动、休眠唤醒、切网及有效缓存恢复中保留设备、节点选择和本地规则；登出、换号、封禁、到期、耗尽、撤销、缓存篡改及许可过期均不越权。
3. 主控制入口故障期间，已连接用户持续下载/请求不中断；恢复控制服务不重启核心、不改变固定出口。节点实际失败独立检测并明确显示，不假报恢复。
4. 服务端刷新已提交但响应丢失、重复点击、并发账号同步及授权兑换的测试不误撤销凭据、不重复下单或扣款；没有幂等契约的写请求不跨入口重放。
5. 新账号浏览器授权、已有桌面会话续期、本人配置、受控节点真实 HTTPS、更新索引及安装包完成端到端验收；未知域、错误证书、错误签名和清单回滚均拒绝。
6. 前端、Rust、PHP、真实 Mihomo 回归及三平台构建按改动执行；四目标构建、Release 附件/签名、独立分发 URL、覆盖升级和实际生产验收分项报告。版本号仅实施可发布改动时更新。

## Risks

应急版不能保证一个备用域名长期不受阻；增加域名与线路需要维护证书、探测、分发和清单密钥。离线许可引入最长许可期内客户端无法获知新状态的窗口，节点端仍须执行限制。保持用户登录依赖原凭据仍有效、系统凭据库可读；无法承诺所有客户零次重新登录。单个国内网络的成功不是全国稳定性证明。

本次交付为规划文档，未实施客户端/服务端逻辑、购买域名、迁移 DNS、发送公告或部署。优先顺序为 P0 验收恢复路线 → P1 恢复版 → P2 缓存与断网恢复 → P3 动态清单和持续观测；P1 可先形成最小恢复交付，P2/P3 不阻塞当前修复。上线若出现误退出、固定出口改变或业务写入重复，停止扩大分发并恢复已验证的可达入口/兼容逻辑；不把已不可达的旧版作为唯一回滚方案。
