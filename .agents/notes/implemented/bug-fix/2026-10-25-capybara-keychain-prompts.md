# Agent Note: 卡皮巴拉钥匙串授权由用户发起

Status: implemented

## Problem

用户确认打开应用即出现 macOS 钥匙串密码弹窗。本机 /Applications/Capybara.app 为 alpha.1，窗口显示凭据库读取失败；代码在 setup 中直接读取续期令牌。钥匙串会在锁定或当前程序未获条目访问许可时要求授权，临时签名版本也无法保证跨构建的信任身份稳定。

## Decision

继续复用系统凭据库，macOS 启动读取、后台令牌轮换及失败清理均禁止钥匙串交互。需要授权时返回可恢复状态并展示说明，只有用户点击恢复登录、提交账号登录或退出登录才允许对应凭据操作弹出系统授权。恢复失败不自动重试；不修改钥匙串 ACL、不关闭系统保护、不把令牌改存明文。

所有凭据操作经同一个同步互斥入口；Security.framework 的交互开关只在同步调用期间关闭，按原状态恢复，不跨 await。macOS 保持服务名，按当前可执行文件 SHA-256 派生 v2 凭据账号名；不主动读取或覆盖旧构建条目。相同二进制移动路径或重新启动仍使用同一条目，更换构建后重新登录一次网站账号。Windows/Linux 保持原账号名。后台轮换写入失败继续撤销新令牌、清空内存并要求重新登录。

用户试用第一轮修复后反馈每次登录仍需密码。核对 keyring/security-framework 的 set_generic_password 发现覆盖旧项前也会读取旧秘密，仅推迟 resume 并未覆盖登录写入。最终增加按构建隔离，重新登录直接创建当前程序拥有的条目；不以“点击恢复”作为旧权限问题的唯一出口。

- 官网首页、下载分发及节点笔记与本次授权流程无关；未发现其他钥匙串提案。

## Alternatives considered

- 直接要求用户每次选择始终允许，改动最少，但仍在启动时打断用户，也无法覆盖锁定钥匙串或升级后的身份变化。
- 改用应用目录文件可以绕开钥匙串提示，但失去系统凭据保护，不能作为便利性优化。
- Developer ID 签名能建立稳定发布身份，属于后续发布条件；当前没有已配置的证书，不能以此阻塞本次可独立完成的交互修复。

- 只按版本号划分条目容易实现，但同版本本地/CI 包或重编译仍有不同临时签名；使用二进制摘要保证与实际构建对应，避免把旧项授权问题重新带入。

## Testing

14 项前端、11 项常规 Rust、2 项发布校验通过。覆盖静默恢复、拒绝后重试、后台写入失败撤销、交互状态恢复、相同二进制跨路径身份稳定和不同构建隔离。前端覆盖一分钟轮询不调用恢复命令、点击才调用、等待时禁止重复操作和失败后仍可登录。额外一项 macOS 真实钥匙串集成通过：三个独立进程静默创建、读取轮换、读取删除测试条目，不访问用户令牌。应用安装、四目标构建及发布证据见[进展](../../../../progress-log.md#2026-10-25卡皮巴拉钥匙串重复授权修复)。

## Consequences

macOS 的交互开关是进程级，需要所有凭据操作统一串行；真实系统授权由用户完成。优化不承诺所有版本之间永远无需授权，也不覆盖网络设置的管理员权限。旧构建条目留在钥匙串中，不绕过权限读取/删除；不可访问的旧会话不能代为撤销，沿用服务端令牌到期或账号设备管理。每次新构建可能需要重新输入网站账号密码，此成本持续到具备稳定发行者签名。生产更新索引的分发与 GitHub Release 分开记录。
