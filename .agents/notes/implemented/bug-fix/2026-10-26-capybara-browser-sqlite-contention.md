# Agent Note: 浏览器授权兑换的 SQLite 写竞争恢复

Status: implemented

## Problem

生产只读诊断 40220840231 证实：2026-10-26 02:06:41，alpha.11 授权请求在 ClientBrowserLoginService 第 92 行兑换时发生 SQLSTATE HY000 database is locked，随后被客户端取消。SQLite WAL 读事务升级为写事务时，其他连接的提交使快照失效，busy_timeout 不能解决这种竞争。

## Decision

在授权服务内对数据库并发错误进行最多五次完整事务重试，回滚完成且事务层级为零才允许重试，短暂退避后重新读取批准状态、封禁状态、设备限额并创建令牌。重试耗尽返回专用 AUTH_BROWSER_BUSY；客户端仅对该明确未提交的错误继续等待，其余响应丢失或网络失败仍不重放一次性兑换。

- [钥匙串处理](../../implemented/bug-fix/2026-10-25-capybara-keychain-prompts.md)：无关，本次错误发生在数据库兑换、尚未写本机凭据。

- 未发现其他活跃 SQLite 浏览器兑换竞争笔记。

## Alternatives considered

- 只提高 busy_timeout 改动少，但不能恢复 WAL 已失效的读快照，生产已有 30 秒设置仍失败。
- 客户端对所有 5xx 和超时自动重放更容易掩盖故障，但无法证明前一次兑换未提交，可能丢失已发出的令牌，因此仅重试明确已回滚的专用错误。
- 改为全局 BEGIN IMMEDIATE 能提前排队写锁，但扩大到其他业务并增加未批准轮询的写锁竞争，本次限定授权事务。

## Testing

用真实文件 SQLite WAL 和两个独立连接在读取批准状态后注入提交，证明失败事务回滚后能成功且仅产生一对令牌；持续竞争时批准保留、无半写设备/令牌、恢复后仍可兑换；非并发错误不重试。原生测试验证专用忙碌继续等待、通用异常不重放。本地并发 3 项 / 24 断言、全套 Desktop 60 项 / 548 断言、前端 30 项、脚本 12 项、Rust 16 项通过（1 项手工钥匙串测试忽略）。旧代码在同一真实 WAL 竞争测试中返回 500，修复后通过。正式版 0.1.0 全平台发布、官网签名更新索引同步及本机授权证据见根目录进展。

## Consequences

重试仅允许完整回滚后的事务，不能覆盖提交结果不明的网络故障；长期数据库写压力仍可能超出五次预算，客户端应在原五分钟期限内等候。
