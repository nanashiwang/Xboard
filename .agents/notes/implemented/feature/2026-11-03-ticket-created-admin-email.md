# Agent Note: 新工单通知管理员邮箱

Status: implemented

## Problem

用户要求客户发起工单时也向管理员发邮件。现有 TicketService 仅在管理员回复后向客户发信；客户创建入口和提现工单共用 createTicket，Telegram 插件是独立可选渠道。

## Decision

在 createTicket 的数据库事务成功提交后，复用 SendEmailJob、send_email 队列、MailService 与 notify 模板，分别向未封禁且邮箱有效的 is_admin 账号发送新工单通知，规范化邮箱去重。无需新增邮箱配置；不包含仅 is_staff 的账号。正文包含工单编号、客户邮箱、主题和首次消息，使用 content_mode=text 转义客户输入；链接使用站点公开地址，不将隐藏后台入口写入邮件。

创建流程异常统一由 catch 回滚一次，避免原重复工单检查和消息失败分支二次回滚外层事务。通知不套用客户回复邮件的 30 分钟缓存，每张成功创建的新工单独立通知。事务回滚、创建失败不发；通知入队故障仅记录工单/管理员 ID 和异常类型，不使已提交工单返回失败，各管理员独立入队。沿用现有最多三次发送尝试和邮件日志，不新增 outbox 或历史工单补发机制。客户后续回复、管理员回复及 Telegram 规则保持各自原有行为。

## Alternatives considered

- 新增专用收件邮箱设置：适合固定客服邮箱，但目前管理员账号已有邮箱，增加配置入口会扩大本次需求；先复用管理员身份。
- 直接在控制器发送：代码短，但会遗漏提现等共用创建入口，且可能在事务尚未提交时通知；收敛在服务提交后。
- 持久 outbox：可以恢复提交与入队之间的故障，但需新增表、调度及补偿规则。本次沿用现有事件邮件队列，明确记录这一交付边界。

## Consequences

复用管理员身份和既有邮件基础设施，无额外配置和迁移；不同管理员分别收件。SMTP/队列不可用时仍需运维处理；入队失败或提交后进程退出不能自动恢复通知，队列重试也不是严格一次投递。没有有效管理员邮箱时只记录警告，不阻止客户提交。发给所有有效管理员，未新增按管理员选择退出。SMTP 接受不等于收件箱送达。

若业务要求通知不可丢失或实际出现入队失败，应重新评估持久 outbox 与补偿扫描；目前告警日志是人工定位入口。
