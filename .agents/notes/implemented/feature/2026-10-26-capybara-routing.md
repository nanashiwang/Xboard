# Agent Note: 卡皮巴拉分流模式与本地规则

Status: implemented

## Problem

用户反馈当前客户端只能显示“规则分流”，无法像原有客户端一样切换规则、全局等模式，也不能修改分流规则。现有净化配置固定 mode=rule，并且节点控制接口隐藏 GLOBAL，单加模式按钮会产生全局模式仍选择直连或节点选择不生效的问题。

## Decision

首页提供规则、全局、直连三种模式与规则管理。规则以域名、域名后缀、IPv4/IPv6 网段匹配，目标为直连、拦截或当前订阅真实组/节点，支持修改、删除与顺序调整；按列表从上到下匹配，置于订阅规则之前。规则仅在规则模式参与分流，不接受任意 YAML 或外部 providers。

原生层管理本地持久化设置、校验与应用，内核运行时热更新并确认，失败保留旧设置；未启动时只保存供下次准备节点使用。订阅更新及内核重启继续应用设置。全局模式生成显式 Mihomo GLOBAL 选择器，仅列实际节点，已选节点在配置里置首，避免默认 DIRECT 及 PUT 后再选节点产生的短暂直连。GLOBAL 选择落盘，由 select_route 独占更新；规则编辑保存忽略前端可能过时的 global_target，保留原生最新选择。断开/连接仍由原系统代理生命周期负责，模式不替代连接开关；[节点即连接决定](./2026-10-27-capybara-select-connect.md)提供主动点击节点的连接入口。

## Alternatives considered

- 仅通过 PATCH /configs 切换 mode 操作较轻，但不能持久化完整用户规则，且后续订阅 reload 会覆盖选择；以本地设置覆盖净化后的配置并统一热更新。
- 开放原始 YAML 编辑能覆盖所有 Mihomo 功能，但会引入监听、路径、provider 和节点凭据编辑边界，且常见分流需求不需要这些权限；采用结构化规则和明确真实目标。若后续确有进程规则或规则集需求，再单独扩展类型与验收。

## Consequences

用户可以直接管理常见分流需求，代价是维护持久化设置、订阅失效目标和失败回滚的状态契约。订阅删除已选全局节点时自动选现有真实节点；自定义规则目标消失时保留旧内核和明确错误，并把新订阅目标提供给编辑器。无法恢复旧配置时停止内核并沿用系统代理恢复，避免显示成功而使用未知配置。

模式作用于被系统代理接管的新连接，既有连接可能沿用原出口。全局模式只列实际节点，自动测速组仍可在规则模式使用；直连模式不等于关闭系统代理。规则保存在本机，不跨设备同步；不接受原始 YAML、外部规则集、进程规则或 TUN 配置。官网分发、已安装客户端与 GitHub Release 分别验证，不把构建成功替代实际使用。
