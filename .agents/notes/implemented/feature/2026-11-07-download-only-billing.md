# Agent Note: 用户套餐只计下载流量

Status: implemented

## Problem

用户明确要求进入节点的上传免费，仅节点发给用户的下载扣额度，并询问直连是否计费、是否因转发双向造成四倍。此前用户额度和日统计都按 `(u+d)×rate`，节点运维统计是原始双向字节；不能把一次下载在网卡的接收/发送直接视为两次用户计量。

## Decision

统一在 UserService 上报入队时快照 `traffic_billing_mode=download_only`。TrafficFetchJob 与 StatUserJob 复用相同方向选择，仅下载乘既有节点倍率，上传不增加用户已用额度或计费日统计。原始任务数据及 StatServerJob 双向运维统计保留，以便带宽核查；用户页面改为计费口径并说明上传免费。

旧排队任务缺少标记时保留旧双向规则，避免重试期间改变既有任务语义；上线后新接收上报用新规则。旧账户 u/d 和历史日报不追溯改写。审计按任务快照计算扣量，不能把新用户 u=0 解读为没有真实上传。

## Related decisions

活跃笔记已检索：[审计](../../implemented/process/2026-11-07-traffic-accounting-audit.md)部分重叠，历史快照保持并补充新口径；[统计事务](../../implemented/bug-fix/2026-11-07-traffic-stat-retry-atomicity.md)继续约束失败回滚；[倍率决定](../../implemented/simplification/2026-10-22-node-names-and-residential-rate.md)保持倍率，新的计量方向由本篇负责。没有需合并或拒绝的活跃提案。

## Alternatives considered

- 在节点把上传计数清零实现最直接，但要升级多台节点，也会丢失运维双向统计；选择面板统一控制套餐口径。
- 直接修改两个任务的所有上传字段会影响旧排队任务，且容易使用户额度和日统计规则不一致；用显式入队快照和共用方向选择。
- 追溯清零所有用户历史上传可立即减少旧用量，但会改变既有已结算周期和历史证据，本次只切换新上报规则。

## Verification

本地 Operations/耗尽提醒 28 项/170 断言通过，含上传独占、下载独占、双向、1×/2×/5×、旧任务、空上报与失败回滚；前端相关 10 项及 JS/PHP 语法通过。面板 CI 与双架构镜像已完成（0f3883f）；Release 和生产尚未完成。固定节点源码 0a29338 的 UDP 快速复制回归发现方向倒置及写计数被绕过，需先确认并修正节点，再启用生产只下载计费；没有把面板单测当作节点验收。

## Consequences

仅取消上传不会取消既有 2×/5×；反馈账号账面 u 约占扣量 5%，但 UDP 方向误记使其不能代表全部真实上传或准确节省比例。客户端 DIRECT 不经过节点，不会进入上报链路；客户端模式只存本地，面板无法从节点用量推断当前规则/全局。客户端规则选择走代理的请求仍按下载扣量，包括服务器侧直接出站的代理请求。上报准确性与提交后 ACK 丢失仍不由本规则证明。
