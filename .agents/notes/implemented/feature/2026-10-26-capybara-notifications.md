# Agent Note: 卡皮巴拉同步官网系统通知

Status: implemented

## Problem

用户要求客户端增加铃铛并同步网页版系统通知。官网 user/notice/fetch 和现有公开 Desktop /notices 都读取 v2_notice 的 show=true 公告；客户端没有入口。网站当前没有账号级已读接口或已读表，不能宣称两端已读状态互通。

## Decision

复用现有 Desktop /notices，原生独立请求固定官网地址，不占用账号/节点互斥锁，不携带账号令牌。每页二十条，启动、打开及每五分钟刷新，保留服务端排序；切页和迟到请求不得混淆。侧栏铃铛显示已加载公告的未读红点，弹窗支持详情、分页、刷新及本页已读；只读详情才标已读，标记按公告 ID 和内容指纹保存在本机，内容变更重新提示。获取失败保留旧数据并显示同步错误。

使用 marked 解析 Markdown，DOMPurify 严格标签/属性清单清理兼容的 HTML 公告；不执行脚本、不加载远程图片，不更改 WebView CSP。图片提供显式查看入口，正文链接由受限 Rust 命令校验 HTTP(S) 后在系统浏览器打开。没有桌面通知推送和弹窗强制打断，不新增服务端协议或改官网。

## Alternatives considered

- 新建账号级已读服务可以跨设备同步，但官网没有对应能力，扩大了数据库与网页改动；本轮同步内容，本机保存已读。
- 直接加载官网 iframe 可以复用页面，但引入登录/导航及 WebView 权限耦合；使用已有专用只读 API。
- 直接展示服务端 HTML 可以还原格式，但会把外部内容放入有原生命令的页面；采用清理后的有限排版和受限链接。

## Verification / Testing

- 同一公开公告源，隐藏通知不出现，分页/失败/空状态正确，读标记跨重启保留、编辑后恢复未读。
- 关闭/重开、明暗/760px、正文链接与恶意 HTML 有验收；同步不影响连接/切换/登录。
- 前端/原生/现有后端通知回归与构建通过，发布四目标、核实资产/官网分发，记录本机安装和生产内容比对。

## Consequences

已读仅本机，红点只反映已加载通知；浏览器跳转由用户触发；网络失败不是无通知。Windows/Linux 构建与真机分别记录；不把系统通知中心入口解释为 OS 推送。


本地前端合并 50 项、脚本 16 项、Rust 23 项通过，已有钥匙串人工测试忽略 1 项；类型与 Vite 构建通过，新增生产依赖审计无已知漏洞。通知 API 后端回归 1 项 / 10 断言覆盖公开/隐藏和分页。前端覆盖已读持久化、正文变更、切页迟到响应、失败保留、空状态、五分钟刷新、存储失败及恶意 HTML；Rust 覆盖内容指纹、响应边界、不携带账号凭据和危险链接拒绝。

CUA 在明确标记模拟数据的预览中确认明暗主题、760×620 最小窗口、正文内部滚动、已读后重载、空态、失败重试与 Esc 关闭。正式公开 API 当前返回零条公告；不向生产写入测试公告。Windows/Linux 真机、安装版和发布/分发的最终结果另记进展，不以预览替代生产。未来若网站增加账号级已读协议，再评估跨端已读同步。
