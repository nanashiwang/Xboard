# Agent Note: Go 与 Hub 客户端恢复通道

Status: implemented

## Problem

用户要求 Go 不可达时 Hub 接管登录、订阅同步、更新检查及下载，再通过新版或可信入口清单迁到新域；明确排除第三方客户端自动恢复。原生 0.1.13 固定 Go，Hub 只有静态导航和 GitHub 链接，旧版不会自动获知新增域名。用户已授权代码、中文提交推送、版本发布和部署。

## Decision

0.1.14 内置 `https://capybarago.uk` 与 `https://app.capybarahub.fyi`。Hub 根页继续 Cloudflare Pages，备用应用子域通过 Cloudflare 严格 HTTPS 直接到同一权威账号源站，绕过 Go 的域名和跳板；复用设备、令牌、套餐及订阅权限。入口运维只创建专用 vhost，不修改主设置、节点路由或支付回调。公网健康接口只返回服务标识和协议版本，不含用户数据；受保护接口维持原鉴权。

[入口目录](../../../../desktop/capybara/src-tauri/src/entries.rs)先获取不带凭据的签名入口清单，然后以不带凭据的健康探测选择服务。单个探测3秒、成功结果复用30秒，发现清单至多每分钟请求一次。普通 GET 网络/5xx/HTML异常最多切换一次；浏览器授权开始前选路，之后固定同一入口。刷新、订单、支付、兑换等写操作只执行一次，不在结果未知时跨入口重放。网络错误或未识别的401/403不作为清除刷新凭据的依据；明确撤权仍遵守原规则。已有核心和登录记录沿用原保护边界，离线冷启动未在本轮实现。

`service-entrypoints.json` 明确用途、单调序号、签发/到期时间、最多4个HTTPS规范源站；发行流水线用现有更新私钥生成 `capybara-entrypoints.json` 信封，客户端用原固定公钥验签后缓存。范围限制、有效期、同序号内容冲突和版本回退都会拒绝；多任务写缓存串行，并先回读已接受的最高序号。测试私钥仅在生成夹具时驻留内存，仓库仅含公钥和签名。当前清单有效180天；更新域名要先部署并验收新入口，再增加序号重签发布。未知网页地址、URL参数和重定向不能引入带凭据的目标。

[更新器](../../../../desktop/capybara/src-tauri/src/updates.rs)分别检查 Go 和 Hub 索引，处理主索引错误/204/内容异常，保留可用的较新版本。安装包严格限定两域的精确版本化路径；下载或验签失败尝试另一域的同版本包，保留原发行签名和用户确认安装，不降级安装、不在下载前退出。旧 `capybara-latest.json` 继续使用taige包URL，`capybara-current.json` 使用Go，新增 `capybara-hub.json` 使用Hub；三份索引指向同一批签名附件。

[Hub构建](../../../../.docker/hub/build.py)从已核验发行清单复制两个小型恢复JSON到Pages静态存储（no-store、不经过Worker计费请求）；[下载Worker](../../../../.docker/hub/worker.mjs)只代理清单白名单内的GitHub固定版本包，支持GET/HEAD与单Range，重定向只允许GitHub官方附件域，绝不转发用户Cookie/Authorization或返回上游临时下载链接。完整包存储在GitHub，不依赖Go域名或应用源站。导航提供备用官网、Hub下载和GitHub链接，邀请仅透传既有公开邀请码。

## Existing decision audit

- [恢复总提案](../../proposed/architecture/2026-11-02-client-entry-resilience.md)：部分落地。本篇接管本轮双域恢复实现；离线许可、双后端、四域长期容灾仍为提案，不一并宣称完成。
- [Hub/Go网页分工](2026-11-02-hub-application-domain-split.md)：部分取代原“Hub只做静态导航”的边界，根页保留，增加下载Worker和应用子域。
- [应用更新](../feature/2026-10-24-capybara-updates.md)、[浏览器授权](../feature/2026-10-25-capybara-browser-login.md)：沿用更新公钥、安装身份和单次授权入口固定契约，增加先选路和独立下载恢复。
- 既有香港入口及Windows兼容未提交修改无关，保持原归属；第三方客户端自动切线明确不实施。

## Alternatives considered

- 仅在Hub放新版安装链接：能手动恢复，但旧客户端不会自动使用，订阅同步也仍被单域阻断，因此增加原生主备选择。
- 每次换域都发布新客户端：交付直观，但包体大且需要安装；新增签名清单支持仅换域时更新地址，保留客户端版本更新作为另一条恢复路。
- Hub重定向到Go或仅镜像索引：维护少，但被阻断的域名仍是必经路径；备用服务直接回源、包由GitHub独立存储。
- 遇到错误就重放所有请求：恢复表面简单，但会重复刷新令牌、兑换或下单；本轮仅安全GET重试，写请求保持一次执行。

## Consequences

客户端需先升级到0.1.14才具备兜底能力；失联旧版仍可能需要覆盖安装。两入口共用账号后台，并非服务器/数据库灾备；Hub及其应用子域共用一个注册主域，也不承诺同时受阻时仍可恢复。GitHub附件存储及Cloudflare配额是备用下载依赖，入口清单到期后回退内置地址，运维需要在到期前更新签名清单。第三方客户端不增加自动切换；用户从备用官网重新导入时，网站通过固定配置白名单生成备用域名订阅链接，主订阅设置和其他Host保持原行为。该修正避免重新订阅仍拿到Go地址。未追加通知客户、购买服务或更改第三方订阅客户端。

本地验证与生产状态分开记录在[进展](../../../../progress-log.md#2026-11-03客户端-gohub-自动兜底)。本地测试包括故障入口无凭据探测、已验证入口GET失败切换、写操作不重放、网络错误保留登录、签名篡改/过期/回退拒绝及下载代理隔离。发布必须验证四目标构建、21附件与原公钥验签，部署必须验证备用登录/订阅和完整下载，不能用HTTP200代替真实用户流程。

首次Pages生产验收暴露Worker第三参数契约：运行时传入ExecutionContext，而测试直接传fetcher。默认导出改为两参数包装，只由隔离测试注入fetcher；新增按运行时三参数调用默认导出的回归，防止元数据正常但所有安装包502。

本机GitHub附件吞吐较低；保留已完成的ARM包和Windows Hub完整包验签，增加手动只读Verify Capybara Distribution工作流，在GitHub runner回读21个Release附件及Hub的7个完整包、2个恢复JSON，逐文件验证大小/摘要并用原公钥验证两条路径的四目标更新包与入口信封。该流程不修改发布指针，不使用生产账号，也不能代替中国大陆运营商或用户实机验收。
