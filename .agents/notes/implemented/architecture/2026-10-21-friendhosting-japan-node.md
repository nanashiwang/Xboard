# Agent Note: FriendHosting 日本普通套餐节点

Status: implemented

## Problem

用户要求将新日本服务器接入各套餐，但排除独享套餐。生产普通套餐对应权限组 1–4，独享套餐对应权限组 5；新节点不能因复用已有美国后端记录而继承独享授权。

## Decision

复用现有第一阶段 TLS / WebSocket 入口，通过独立 WireGuard peer 到日本 xboard-node。公开订阅记录与隐藏机器后端均只允许权限组 1–4，不创建固定出口池记录。公开节点 #354 关联后端 #353 和机器 #18；隐藏阶段完成真实代理及独享身份拒绝检查后，节点已公开并加入现有探针。

日本机约 458 MB 内存，使用现有已验证的原生节点二进制与非 root systemd 服务，避免额外容器运行时。后端 31443 仅允许隧道入口或回环；日本 SSH 3333 保持原登录方式。新 peer 使用精确 /32，不改变任何服务器默认路由。

## Existing decision audit

[第一阶段架构](../../implemented/architecture/2026-10-17-stage1-replacement.md)部分重叠，继续复用入口与防火墙约束；[固定出口池](../../implemented/feature/2026-10-19-owned-fixed-exit-pool.md)说明独享分配边界，本次不扩池。本地未提交香港迁移记录属于此前工作，保留其原归属。

## Alternatives considered

- 日本公网直接提供代理可以绕开共享入口，但会新增独立客户端协议、证书及暴露面；本次复用现有订阅与加密中转契约。
- 克隆美国节点后保留全部权限组操作简单，但美国后端已包含固定套餐授权；必须显式重置为普通套餐组并验证独享 UUID 拒绝。
- 容器部署便于镜像管理，但新机内存有限且已有原生节点安装惯例，因此复用原生服务与受限配置。

## Testing

三名普通账号通过严格 TLS 的 ipify、日本 Cloudflare trace、gstatic 请求及 UDP DNS；独享账号和无效 UUID 均被拒绝。普通套餐节点数为 15/16/17/18，独享仍为原固定出口与香港备用。原美国、香港、CF 线路抽查通过，旧节点关键配置及套餐参数与备份一致。机器服务和心跳已核对；18 条质量探针范围、14 条入口隧道映射已保存，NAS 首轮有超时、本机追加两轮 5/6 成功，间歇波动继续保留；持续采样结果另见[进展记录](../../../../progress-log.md#2026-10-21friendhosting-日本节点接入)。

## Consequences

复用现有客户端协议和机器管理，降低独立证书与客户端迁移成本，同时增加一个 peer、路由和监控映射的维护工作。共享入口仍是公共单点。短期检查不证明大陆各运营商性能、长期容量或整机重启恢复。备份包含敏感配置，仅在服务器受限目录保留，不提交仓库。
